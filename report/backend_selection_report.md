# Backend selection v2: vLLM vs llama.cpp on Xeon Max (HBM, cache mode)

*Experiment `backend-selection-v2`, CRESCO8, 3–4 October 2026. All numbers come from `processed_results/`
and are regenerated by `scripts/analysis/summary_tables.py` (full tables: [`tables.md`](tables.md)).
Figures are in [`../plots/`](../plots), each with its data in `plots/data/`.*

## 1. Objective

The rest of the thesis studies **online, concurrent LLM serving** on the Xeon Max: raising concurrency,
watching how the HBM/DDR memory system is loaded, and maximizing aggregate throughput. This experiment
selects the backend those experiments run on.

The first selection study compared `vllm serve` with `llama-bench`. Those tools measure different things: a
batching server versus single-sequence forward passes. This version answers the question with:

- **server vs server** (`vllm serve` vs `llama-server`) through **one shared client**, the primary criterion;
- separate **offline engine microbenchmarks**, reported as such;
- **memory-traffic telemetry** recorded during every online run and normalized by the measured sustainable bandwidth.

The question is not "which is faster" but:

> Which backend is the stronger experimental platform for concurrent, throughput-oriented inference and for
> studying how the HBM memory system behaves as load increases?

## 3. Fairness methodology

**Identical for both servers:**

- **Client.** One closed-loop client, `scripts/bench_client.py` (standard-library asyncio, one fresh
  connection per request), with the same request body and the same timing points.
- **Prompts.** Prompts are **token-id lists**: BOS + ISL−1 pseudo-random ordinary tokens, deterministic per
  request. Both servers therefore receive exactly ISL tokens, with no tokenizer or chat-template difference and
  no shared prefixes. The prompt manifest SHA-256 is identical across the repetitions of every point.
- **Output length.** `max_tokens = OSL`, `ignore_eos`, `temperature 0`. Every request is checked:
  `usage.prompt_tokens == ISL` and `usage.completion_tokens == OSL` held for **all 27,672 measured requests**.
  Both servers stream exactly one chunk per token, so chunk timestamps are token timestamps.
- **Server state.** A fresh server is started per concurrency point, sized for exactly C full-length
  sequences. llama.cpp gets `-np C -c C·ctx_slot`. vLLM gets `VLLM_CPU_KVCACHE_SPACE` = C · seq_len · KV
  bytes · 1.15.
- **Per-point procedure.** Each point runs a 10 s idle baseline, then warm-up, then 3 measured repetitions.
- **Load.** The client runs a closed loop with C workers × 3 requests each, so C requests are always in
  flight. Workers' start times are spread over one estimated request duration, so in-flight requests are at
  different stages.
  - Throughput is measured in the **steady-state window**: from the moment every worker has its first
    token, to the moment the first worker finishes.
  - Latency statistics use the requests whose whole life lies inside that window.
- **Sweep rule**, declared before any measurement and applied identically to every arm:
  - Run C = 1…64.
  - Stop after two consecutive doublings that each add less than 5% throughput.
  - Extend to 128 and 256 only while the last doubling added at least 10%.
  - Skip any point projected to take more than 4 h. No point was skipped.

**Backend-specific tuning** (`processed_results/tuning.csv`) used a small grid on the 8B balanced workload
at C = 1 and 16. The rule: highest steady throughput at C=16, unless C=1 TPOT worsens by more than 5%.

| Arm | Tried | Chosen | Effect |
| --- | --- | --- | --- |
| vLLM | `max_num_batched_tokens` 2048 / 4096 / 8192 | 8192 | all within 1% |
| llama.cpp BF16 | flash-attn on/off × ubatch 512/2048, KV bf16 | FA on, ub 512 | FA on +17%. ub within 1%. KV bf16 −19% |
| llama.cpp Q8_0 | same | FA on, ub 2048 | FA on +23%. ub2048 +2.3%. KV bf16 −19% |

The tuning was repeated once after a client bug was found (§9). The first run is kept as
`tuning-v1-queue-bug`.

**Unavoidable differences.**

1. **Weight files differ in format.** vLLM loads safetensors and llama.cpp loads GGUF. The BF16 values are
   identical.
2. **KV cache precision:** vLLM uses BF16 and llama.cpp uses F16. Both are 2 bytes per element, so the memory
   traffic is the same. llama.cpp with a BF16 KV cache was 19% slower, so F16 was kept.
3. **CPU binding.** vLLM pins its compute threads itself (`VLLM_CPU_OMP_THREADS_BIND=0-54`); llama.cpp is
   pinned by OpenMP (`OMP_PROC_BIND=close`, 55 threads). Both end up on cores 0–54.
4. **Process structure.** vLLM's HTTP front end is a separate process, while llama.cpp's HTTP threads live in
   the same process. Both are limited to cores 0–55.

## 4. Validity checks

| Check | Result |
| --- | --- |
| Failed requests | 0 of 27,672 (online, `main` campaign) |
| Token counts | exact for every request, both servers |
| Repeatability | 3 repetitions per point. Median coefficient of variation of throughput 0.17%, maximum 6.0% (1B vLLM, C=32) |
| Client not a bottleneck | client CPU ≤ 0.30 of one core. Event-loop lag ≤ 43 ms (1B vLLM at 4–5k tok/s), median ≈ 0.1 ms |
| Server cores free | compute-core busy during each point's idle baseline ≤ 0.85% |
| Node health | per-job STREAM check (8 GiB, 55 threads, socket 0): 490–527 GB/s on every campaign node. Jobs below 450 GB/s abort automatically |
| Weights in the right memory | `numastat` per point: llama.cpp 15.5 GB and the vLLM worker 21.4 GB of private memory, all on node 0 |

**Telemetry.** Unprivileged users can't read uncore counters on CRESCO8 (`perf_event_paranoid=2`, no root,
no `perf`/`pcm`). That rules out DDR IMC CAS, the HBM controllers, the M2M near-memory-cache tags and RAPL.
Memory traffic is therefore measured per server thread from the core side, with Intel's Sapphire Rapids
offcore-response events:

- **reads:** `OCR.READS_TO_CORE.L3_MISS_LOCAL`;
- **writes:** `OCR.WRITE_ESTIMATE.MEMORY`;
- **AMX activity:** `EXE.AMX_BUSY`.

These events were validated in four ways:

1. **Against STREAM.** STREAM triad under the same sampler, at working sets of 4–96 GiB, gives PMU reads +
   writes = **0.97–1.00 × STREAM's modeled traffic** (`stream_calibration.csv`, figure `stream_calibration`).
2. **Against a first-principles model of the servers' traffic.** The model is: forward steps/s × the bytes
   a step streams (all weights except the input-embedding table: 15.01 GB for 8B BF16, 7.97 GB for Q8_0, from
   the file headers) + decode tokens/s × context × KV bytes per token. Wherever decode dominates, the measured
   reads are 0.96–1.18× the model for vLLM (median 1.01) and 0.96–1.52× for llama.cpp (median 1.05 BF16, 1.15
   Q8_0). The model is a lower bound: activations, attention intermediates and prefill attention are left out,
   and the excess grows with batch. Where prefill dominates, measured traffic reaches 2.4× the model.
3. **Overhead.** A first event set (7 events, two of them multiplexed) slowed vLLM decode by 4.5% and
   llama.cpp by 1.3%. The final set has 5 events and no multiplexing. Its overhead is ≤ 1%, within run-to-run
   noise, for both servers (A/B/A/B on one node).
4. **Discarded events.** `OCR.HWPF_L3` read exactly 0 in every run, and `LONGEST_LAT_CACHE.MISS` matched the
   OCR reads within 0.2%, so both were dropped.

**What the telemetry cannot do.** In cache mode it measures **memory-side traffic as a whole**, i.e. HBM-cache
hits plus DDR. It cannot split the two, and it cannot see the HBM cache's own fills and evictions toward DDR.
Every active working set here is ≤ 47 GiB (weights + live KV), below the 64 GiB HBM cache. "Memory traffic"
below is therefore traffic that the HBM cache serves, apart from conflict misses.

**Baseline.** The sustainable bandwidth is not the theoretical HBM peak. It is **STREAM triad on the same
layout (55 threads, socket 0), measured with the same counters**: ~505–519 GB/s (triad) for working sets ≤ 8 GiB, then
484 / 383 / 302 / 252 / 191 GB/s at 16 / 32 / 48 / 64 / 96 GiB. Utilization is quoted against the ~500 GB/s
maximum unless stated.

## 5. Offline comparison (engine microbenchmarks)

Figures `f01_offline_prefill_*` and `f02_offline_decode_*`. These are each engine's own tool, and they do
not measure identical scopes:

- `llama-bench` and `llama-batched-bench` time forward passes only.
- `vllm bench latency` times `LLM.generate()`, which includes the scheduler and sampling.

8B, balanced shape (tokens/s):

| Phase | Batch | vLLM BF16 | llama.cpp BF16 | llama.cpp Q8_0 |
| --- | --- | --- | --- | --- |
| prefill | 1 | **1,236** | 229 | 430 |
| decode | 1 | 18.4 | **21.7** | 31.1 |
| decode | 8 | **138** | 89 | 127 |
| decode | 32 | **421** | 139 | 229 |

- **FACT.** At batch 1, llama.cpp BF16 decodes **18% faster** than vLLM at the same precision (21.7 vs
  18.4 tok/s), and Q8_0 decodes 69% faster. vLLM prefills **5.4×** faster than llama.cpp BF16 and 2.9×
  faster than Q8_0.
- **FACT.** At fixed batch 32, vLLM decodes 3.0× faster than llama.cpp BF16. The same pattern holds for the
  other shapes and for the 1B model.
- **INTERPRETATION.** Single-stream decode streams the weights once per token. llama.cpp does this with less
  per-step overhead. Prefill and batched decode are matrix-heavy, which is where vLLM's AMX coverage (BF16
  GEMMs and attention) pays off, as the earlier counter study already found.

The offline and online measurements agree:

- vLLM 8B: 1,236 tok/s offline prefill vs 1,219 tok/s implied by the online C=1 TTFT.
- llama.cpp 8B: 229 tok/s offline vs 219 tok/s online.

**Observations.**

1. **llama.cpp wins single-request decoding.** At C=1, llama.cpp BF16 has a 16–18% lower TPOT than vLLM on
   the decode-dominated shapes, and Q8_0 a 40% lower one. vLLM wins TTFT at every C (4.2–7.7× at C=1),
   because of its faster prefill.
2. **vLLM turns concurrency into throughput, llama.cpp largely does not.** On 512→512, the doublings 1→2,
   2→4, …, 32→64 add +97%, +92%, +85%, +70%, +44% and +31% for vLLM. For llama.cpp BF16 they add +58%,
   +55%, +21%, +16%, +10% and −1%. On short prompts vLLM's peak is 23–37× its C=1 throughput; llama.cpp's peak is 4–7×. On long
   prompts llama.cpp gains nothing beyond C≈2–4 (1.0–1.2×), while vLLM still gains 2.5–2.8×.
3. **Latency under load favors vLLM at every C ≥ 4.** At C=32 on 512→512, the median TPOT is 97 ms for vLLM
   vs 397 ms for llama.cpp BF16, and the pooled TPOT p99 is 98 ms vs 398 ms. llama.cpp reaches its throughput
   ceiling with per-token latencies of 0.4–1.2 s.
4. **The crossover sits at C≈2.** Above it, vLLM's advantage grows monotonically to 4.9–6.0× (the 1B model
   reaches 6.5–7.0×).
5. **Both servers batch.** At C=64 on 512→512, llama.cpp processes 109 tokens per forward step and vLLM 118
   (figure `f14_tokens_per_step`). The difference is the **cost of a step**:
   - llama.cpp BF16 runs 1.31 steps/s (763 ms each), against 21.0 steps/s at batch ~2: 16× longer steps for
     ~58× more tokens.
   - vLLM runs 7.09 steps/s (141 ms each), against 18.7 steps/s at batch ~2: 2.7× longer steps.
6. **Effect of Q8_0.** It improves llama.cpp by 1.4–1.6× throughout but does not change the shape of its
   curve: Q8_0 still plateaus at C=16–32 and peaks at 251–277 tok/s.

**Interpretation (supported, not proven here).** Batching is not what limits llama.cpp: its slots fill as
expected. What limits it is the per-token cost of a large batch. That points to the components that grow with
batch × context: attention, plus GEMMs that cannot use AMX at BF16. The earlier counter-based study isolated
attention as llama.cpp's dominant cost (≈ 4.5× vLLM's per cached token). This experiment did not re-isolate it.

## 7. Memory-system behaviour

| 128→512 | vLLM BF16 | 278 (55%) | 272 (54%) | 256 (51%) | 225 (45%) | 197 (39%) | 149 (30%) |
| 128→512 | llama.cpp BF16 | **325 (65%)** | 245 (49%) | 119 (24%) | 78 (15%) | 48 (9%) | – |
| 512→512 | vLLM BF16 | 282 (56%) | 274 (55%) | 238 (47%) | 205 (41%) | 176 (35%) | 140 (28%) |
| 512→512 | llama.cpp BF16 | **319 (63%)** | 200 (40%) | 95 (19%) | 65 (13%) | 45 (9%) | – |
| 4096→128 | vLLM BF16 | 215 (43%) | 150 (30%) | 109 (22%) | 95 (19%) | 86 (17%) | – |
| 4096→128 | llama.cpp BF16 | 93 (18%) | 54 (11%) | – | – | – | – |
| 4096→1024 | vLLM BF16 | 263 (52%) | 245 (49%) | 196 (39%) | 178 (35%) | 154 (31%) | – |
| 4096→1024 | llama.cpp BF16 | 218 (43%) | 96 (19%) | 66 (13%) | – | – | – |

**FACTS.**

- For **both backends and every planned workload, memory traffic is highest at C=1 and falls as concurrency
  rises.** The 1B model shows the same pattern.
- **No run approaches the sustainable bandwidth.** The maximum is 65% (llama.cpp BF16, C=1, 128→512); vLLM's
  maximum is 56%.
- As concurrency rises, the hardware moves toward compute:
  - vLLM's AMX busy fraction rises from 0.4% to 11% (512→512) and 18% (4096→128);
  - compute cores stay ≥ 97% busy;
  - the effective clock falls from 2.37 to 2.04 GHz.
- llama.cpp's cores become less busy at high C: 87% at C=64 for BF16, 81% for Q8_0.

**OBSERVATION and mechanism.** Every forward step reads all weights once (16 GB for 8B BF16), whatever the
batch. At C=1 decode is a weight-streaming loop, the most bandwidth-bound regime this workload has. Batching
amortizes that read over more tokens per step, while the arithmetic per step grows with the batch. The steps
therefore get slower, fewer weight reads happen per second, and memory traffic falls.

The first-principles model (steps/s × streamed weight bytes + decode tokens/s × context × KV bytes)
reproduces vLLM's measured reads with a median ratio of 1.01, and llama.cpp's with a median of 1.05–1.15, in
these regimes. So this is an arithmetic consequence of the workload, not a measurement artifact.

**At equal C, vLLM moves more bytes per second than llama.cpp from C≈4 upward**: 1.5–2.9× at C=8 and
3.9–4.1× at C=64. For example, at C=32 on 512→512, vLLM moves 205 GB/s and llama.cpp BF16 65 GB/s. vLLM completes 4× more forward steps per second at
that batch, and each step reads the weights once.

**KV traffic is the term that does grow with C.** In the model, vLLM's KV reads rise from 2 GB/s (C=1) to
49 GB/s (C=128) on 512→512, but the falling weight term dominates.

The extra long-context shape **8192→256** is still prefill-dominated: TTFT is 6–19 s and only 256 tokens are
generated. Its memory traffic also falls with C (vLLM 214 → 97 GB/s).

Hence the **4096→1024 "long-KV decode"** shape was added (§9). It is decode-dominated over a 4–5k-token KV
cache, the same cell shape as in the tiered-KV report. In this regime **the composition of the traffic
changes with C, but not its total**:

- In the model, vLLM's KV reads grow from 10 GB/s (C=1) to 95 GB/s (C=64) and become the dominant term from
  C≈32. Weight reads fall from 250 to 37 GB/s.
- The measured total still falls, from 263 GB/s (52%) to 154 GB/s (31%), while throughput rises 7.6×
  (83 → 631 tok/s, plateau at C=32–64).
- At C=64 each vLLM step streams ≈ 54 GB (15 GB of weights + ≈ 39 GB of KV), and the measured 154 GB/s
  corresponds to ≈ 0.35 s per step. That is about a third of what the memory system can sustain, so the step
  is not limited by HBM bandwidth.
- llama.cpp BF16 plateaus at C=8–16 (117 tok/s, 1.7× its C=1). Its traffic falls from 218 to 66 GB/s.
- The vLLM ÷ llama.cpp BF16 ratio grows from 1.23× (C=1) to 4.88× (C=16).

**Answer to "does more concurrency increase memory-bandwidth pressure?"** Not in total, for either backend,
in any shape measured. Concurrency increases the **KV share** of the traffic, which makes KV placement
relevant (as in the tiered-KV results). But the steps become slower than the memory system, so total traffic
and HBM utilization fall. vLLM keeps 1.5–4× more traffic flowing than llama.cpp at the same C.

## 8. Saturation analysis

Saturation is claimed only where throughput and memory traffic both plateau while latency keeps rising.

- **vLLM, short prompts.** Throughput plateaus at C=64–128: +2% (512→512) and +9% (128→512) for the last
  doubling, while TPOT doubles (148 → 284 ms). **Memory traffic does not plateau near a limit; it falls**
  (176 → 140 GB/s, 28% of sustainable). Compute is saturated instead: compute cores ≥ 98.6% busy, AMX busy
  10–11%, falling clock. **Verdict: compute-bound saturation, not HBM saturation.**
- **vLLM, long prompts** (4096→128, 8192→256). Throughput flattens from C≈8–16 (later doublings +10%, +7%, +3%,
  +2%, 0%), TTFT rises to 12–19 s and memory traffic falls. Prefill (AMX-bound) dominates. **Verdict: prefill-compute saturation.**
- **llama.cpp.** Throughput plateaus at C=16–32 on short prompts and C=2–4 on long prompts. Memory traffic
  falls to 9–19% of sustainable, and core utilization drops to 81–87%. **Verdict: per-step execution cost
  (not bandwidth, not full core occupancy) limits it.** A plausible but here-unproven cause is the
  serialization and attention cost seen in the earlier study.
- **Long-KV decode (4096→1024).** vLLM plateaus at C=32–64 (+9%, +2%) with TPOT 93 → 453 ms and traffic
  falling to 31% of sustainable while KV reads become dominant. llama.cpp BF16 plateaus at C=8–16 (+10%,
  +4%); its C=32 point was skipped by the 4 h budget rule (projected 4.7 h).
- **Neither backend reaches memory-bandwidth saturation in any measured configuration.** The highest share of
  the sustainable bandwidth is reached at **C=1** (55–65%). The single-stream decode loop has a ceiling at
  roughly two thirds of STREAM, which reflects the per-step synchronization and non-streaming phases of each
  token.

## 9. Deviations from the plan, and incidents

1. **Uncore telemetry unavailable.** HBM vs DDR could not be split (§4). If an administrator lowers
   `perf_event_paranoid` on one node, `telemetry.py` starts reading the HBM and DDR CAS counters and the M2M
   tag hits/misses without code changes.
2. **Two workloads added after seeing data, both reported for all arms under the same rules.**
   - 8192→256 (the plan's optional long-context shape) was enabled for 8B.
   - 4096→1024 was added for 8B because no planned shape is decode-dominated over a long KV cache, the only
     regime in which concurrency raises memory traffic.
3. **Client bug found during tuning and fixed before the campaign.** The first client let workers pull from a
   shared queue. A stagger estimated from a warm-up with simultaneous prefills was 4× too long, so early
   workers consumed the queue and the steady window collapsed (0.5 s). The fix:
   - per-worker fixed request sets;
   - a median-based duration estimate;
   - 3 waves at every C.

   Tuning was re-run, and the first run is archived as `tuning-v1-queue-bug`.
4. **Orphaned vLLM worker.** A cancelled smoke job left a `VLLM::Worker` process spinning on cores 0–54. It
   halved STREAM on hbm01 (497 → 323 GB/s) and doubled TPOT. It was found through the per-job node check.
   Fixes:
   - SIGTERM handling in the runners;
   - orphan reaping in `job.sbatch`;
   - a hard node-check threshold;
   - the per-point idle-core guard.

   Smoke data from that node were not used.
5. **Lustre contention.** Five jobs loading the same 16 GB from the shared HDD pool stalled vLLM model
   loading for over 25 minutes, so the first campaign attempt (`main-v0-lustre-stall`) failed at startup.
   Models are now staged to node-local NVMe at job start. Load time is not part of any measurement.

## 10. Backend-selection rationale

| Criterion | Evidence | Better suited |
| --- | --- | --- |
| Offline engine, single sequence | llama.cpp BF16 decodes 18% faster. vLLM prefills 5.4× faster | split: llama.cpp for decode, vLLM for prefill |
| Online, C=1 | llama.cpp TPOT −16…−18% (Q8_0 −40%). vLLM TTFT 4.2–7.7× lower | llama.cpp for interactive single-user decode |
| Maximum online throughput (8B) | vLLM 631–1,175 tok/s vs llama.cpp BF16 117–176 (Q8_0 212–277) | **vLLM, 5–7×** |
| Scaling with concurrency | vLLM 23–37× over C=1 on short prompts. llama.cpp 4–7×, and ~1× on long prompts | **vLLM** |
| Latency under load | at C=32, TPOT p99 98 ms vs 398 ms | **vLLM** |
| Memory traffic under load | vLLM sustains 1.5–2.9× more GB/s than llama.cpp at C=8 and ~4× at C=64. Both peak at C=1, below 65% of sustainable | **vLLM** (more traffic while doing more work) |
| Reaching sustainable bandwidth | neither does. Highest share is llama.cpp at C=1 (65%) | llama.cpp, at C=1 only |
| Stability / repeatability | 0 failures in both. CV ≤ 1% in almost all points for both | tie |
| Instrumentation | vLLM: Prometheus iteration-token histograms, KV usage, a separate worker process. llama.cpp: decode counters and slots. Both work with the PMU sampler | tie, slight vLLM edge |
| Future HBM/DDR placement experiments | vLLM already has the tiered HBM/DDR KV fork and runs at a wide range of operating points (C=1…256) | **vLLM** |

**Decision: vLLM** is the backend for the next phase, based on the BF16 pair. The INT8 pair (§13) is
prepared and runs next. The reason is not that it is faster in general: at one
request and at matched precision llama.cpp decodes faster and uses more of the memory bandwidth. vLLM is chosen
because the thesis experiments depend on **concurrency**, and only vLLM turns additional concurrent requests
into additional useful work:

- 23–37× its single-request throughput on short prompts, versus 4–7× for llama.cpp;
- per-request latency that stays usable while it does so;
- the memory system kept 1.5–4× busier than llama.cpp at any concurrency from C=8 up.

llama.cpp's throughput stops growing at C≈16–32 (short prompts) or C≈2–4 (long prompts), so most of the
concurrency range the thesis wants to explore would be flat for it.

## 11. Fact / observation / interpretation / conclusion

- **FACT.** Under identical requests, layout and client, vLLM BF16 delivers 4.9–6.0× the throughput of
  llama.cpp BF16 at the highest common concurrency, and llama.cpp BF16 delivers 1.12–1.16× vLLM's throughput
  at C=1 (decode-dominated shapes). Memory traffic falls with concurrency for both backends; its maximum share
  of the sustainable bandwidth is 65% (llama.cpp, C=1) and 56% (vLLM, C=1).
- **OBSERVATION.** Both servers batch equally (tokens per step ≈ C). vLLM's step time grows 2.7× from batch 2
  to batch 118, llama.cpp's 16×. vLLM's AMX use and core occupancy rise with load, llama.cpp's core
  occupancy falls.
- **INTERPRETATION.** The weight read is amortized by batching, so short- and long-prompt serving on this CPU
  turn compute-bound as concurrency grows. vLLM's AMX coverage (BF16 GEMMs and attention) lets its compute
  scale. llama.cpp's per-token cost at large batch (attention, AVX-512-only BF16 GEMMs) caps it early. The
  attention attribution comes from the earlier study and was not re-measured here.
- **CONCLUSION.** For a thesis about concurrent serving and memory-system behaviour under load, vLLM is the
  appropriate platform. It is the only one of the two whose throughput, step rate and memory traffic remain
  responsive across C = 1…128.
  - The hypothesis "more concurrency → more HBM bandwidth pressure" is **not supported** for any measured
    shape, long-KV decode included (prompts up to 8k tokens, outputs up to 1,024 tokens). Concurrency shifts
    the traffic from weights to KV, but total traffic falls.
  - Concurrency makes the workload compute-bound well before HBM is the limit.
  - HBM pressure lives in two places: low-batch decode (weight streaming), and decode over long KV caches,
    where KV reads grow with C × context.

## 12. Implications for the HBM experiments

1. **Flat-mode placement experiments should target two regimes.** The first is **low-concurrency decode**,
   which is bandwidth-bound: weights in HBM vs DDR matter most there. The second is **long-KV decode at
   moderate–high C**, where KV traffic grows with C. The tiered-KV results (c48 and c80 at 4096→1024)
   already sit in the second regime.
2. **Short-context, high-concurrency cells measure the AMX compute ceiling, not HBM.** Keep one as a
   compute-bound control.
3. **Ask for uncore access on one node** (lower `perf_event_paranoid`, or `pcm` with privileges). In flat mode
   the HBM and DDR NUMA nodes can be told apart through placement, but in cache mode only the M2M tag counters
   can split hits from misses.
4. **Keep the per-job STREAM check and the idle-core guard.** On cache-mode nodes, a single stray process or a
   fragmented memory state changes results by up to 2×.

## 13. Prepared, not yet measured: the INT8 pair (vLLM W8A8 vs llama.cpp Q8_0)

The BF16 pair compares the two engines on identical weights, but llama.cpp has no BF16 AMX kernel, so it
cannot use AMX there. A second precision-matched pair removes that asymmetry: both engines run int8 weights
times int8 activations on AMX-INT8.

| | vLLM `vllm-w8a8` | llama.cpp `llamacpp-q8_0` |
| --- | --- | --- |
| Source | same BF16 snapshot | same BF16 snapshot |
| Method | round-to-nearest, no calibration data (llm-compressor 0.14.0 `QuantizationModifier`, scheme `W8A8`, data-free pipeline) | round-to-nearest (`llama-quantize Q8_0`) |
| Weights | int8, symmetric, one scale per output channel | int8, symmetric, one scale per 32 weights |
| Activations | int8, symmetric, one scale per token, dynamic | int8 (Q8_0/Q8_K), per block, dynamic |
| Not quantized | `lm_head`, token embedding (BF16) | none (token embedding and output in Q8_0) |
| Bytes streamed per step (8B) | 8.03 GB | 7.97 GB |
| Kernel | vLLM CPU `int8_scaled_mm_with_quant` (AMX-INT8; chosen automatically for symmetric activations and every Llama shape) | ggml AMX `tinygemm_kernel_amx` (≥ 2 rows), AVX-512 VNNI at 1 row |

The two representations stream almost the same number of bytes per step (within 1% for 8B). Remaining
differences: scale granularity, and lm_head precision (BF16 in vLLM, int8 in Q8_0).
